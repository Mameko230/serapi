## 1. 换行 tag 的编号在原文/译文中不一致（值一致）

**状态**：待评估

**现状**

- 换行 tag `mq:ch` 在 memoQ 中按段分配数字编号，源/译可能不同，但 `val`（换行符内容）一致。
- 写回时已有“优先复用原文原始 symbol”的逻辑：`app/segment_view.js` 的 `newTokenSymbols()` 对 newline token 使用原文缓存的 `mq:ch` 原始 symbol。
- 普通 tag 的复用目前按 `name` 匹配（`sourceTagFor()`），同名不同值的多个 tag 可能匹配错对象，是潜在隐患，需要和本项一起评估。

**方案**

1. 先做“只读验证”，不改行为：
   - 构造含换行 tag 的行，写入译文（用/不用原文 symbol 各测一次），回读 `/rows` 的 target symbols，比较换行 tag 的 `output` 编号与属性；
   - 同步看导出/预览里的编号表现，确认 memoQ 是否会强制重新编号。
2. 若 memoQ 允许保持编号：
   - 保证所有写回路径（保存、Ctrl+Enter 保存+确认、F9 插入后写回）都复用原文 `mq:ch` 原始 symbol；
   - 把普通 tag 的匹配从“只按 name”改成“按 name + 类型 + 属性值 + kind”的签名匹配（和 `app/tag_insert.py` 的 `_tag_sig`、`app/lint.js` 的 `tagKey` 同一套语义），避免同名不同值 tag 被配错。
3. 若 memoQ 服务端强制按目标段重新编号：
   - 把“换行 tag 编号可能不同”写进 `docs/LIMITATIONS.md`，QA/导出以值一致为准，不承诺编号一致。

**风险 / 影响**

- 强制复用编号可能影响其他带值 tag 的配对，尤其是同名多值 tag；必须先补 fixture 再改。
- 改匹配逻辑会影响 F9、写回、QA 三处，必须一起回归。

**验证方式**

- 离线：新增 fixture 覆盖“同名不同值 tag”“多个换行 tag”，断言写回 symbol 与原文一致；
- 真机：`docs/SMOKE.md` N3/N26 之外补一条“写回后换行 tag 编号/值”冒烟。

## 2. 实时 QA 的 Tag 提示与 Tag 长短显示联动

**状态**：待评估

**现状**

- 右下角实时 QA 现在提示形如 `缺少 tag mq:rxt（2 个）`，只显示 tag 前缀名，用户分不清缺的是哪一颗。
- Tag 胶囊本身有“短显 / 长显”设置（`tagDisplay`），由编辑器配置控制。

**目标效果**

- 短显：`缺少 tag #1（2 个）`
- 长显：`缺少 tag #1（item01）（2 个）`（编号 + 值一起显示）
- “多出 tag”同样处理。

**方案**

1. `app/lint.js` 生成 tag 警告时，除了 name，把 `output` 编号和值/显示文本也放进 message 数据（新增 `tagNo`、`tagValue` 字段，向后兼容）。
2. `app/qa.py` / `app/qa_ui.py` 渲染时读取当前 `tagDisplay`（short/long）格式化文案；取不到编号时回退 `缺少 tag <name>`。
3. Tag 显示模式切换时，对当前段重跑一次 QA，让文案立即跟随变化。

**风险 / 影响**

- 只改提示文案与数据字段，不改 QA 规则本身；需要保证旧版 token（无 `output`）也有可读回退。

**验证方式**

- 离线：单测 lint 输出的 `tagNo`/`tagValue` 字段 + 两种显示模式的格式化函数；
- 视觉：`tests/render_main_ui.py` 增加 QA 短显/长显两种截图。

## 3. 性能与跟手感优化（先测量，后优化）

**状态**：待评估

**现状**

- 用户关心 Ctrl+Enter 后“保存 → 确认 → 跳下一行 → 读取新行”的整体体感速度。
- 当前链路：PUT 保存 → 批量 confirm 或逐行动作 → 轮询状态 → 刷新段列表缓存 → 激活/读取下一行；其中状态轮询、列表刷新、下一行读取基本是串行的。

**方案（按顺序做，任何一步单独可回滚）**

1. **先埋测量点**：给“按键到发出确认请求”“确认回执到状态落表”“状态落表到下一行读取完成”打时间戳日志（仅日志，不影响功能），在真机收集典型耗时。
2. **候选优化**（依据测量结果挑）：
   - 保存前预取下一未锁定行的数据/缓存，确认成功后直接装载，省一次往返；
   - 确认状态回执优先走页面已有 SignalR 行更新事件，轮询只做兜底（缩短/按指数退避）；
   - 减少重复的段列表全量刷新，改为按 rowId 单行更新；
   - 与“跳下一行”并行触发 TM/TB 命中、段信息、QA，避免用户看到空面板。
3. **目标**：先在真机测量基线，再确定“确认到下一行可编辑”的目标时长；不做无数据支撑的“感觉优化”。

**风险 / 影响**

- 涉及保存/确认状态机与读取代际，改动必须保持 `save_coordinator` / `read_workflow` 的现有防错语义（行变、文档变、忙碌保护）。
- 并行化不能引入“响应乱序覆盖当前行”的回归。

**验证方式**

- 离线：状态机测试全部保持绿；新增时间戳字段测试；
- 真机：`docs/SMOKE.md` N4 增加耗时记录（源码版 + 打包版各一次）。

## 4. TB 详情排版拥挤

**状态**：待评估

**现状**

- TB 详情在 `app/res_panel.py` 的 `_render_detail()` / `_tb_language_blocks()` 用 HTML 渲染，定义/示例多时部分文字挤在一起。

**方案**

1. 统一详情块的排版规格：语言块之间加分隔间距；术语行、定义、示例各占一行，定义/示例允许换行，不再压缩到一行；
2. 长文本用 `word-wrap` + 合理行高；多语言列表用统一列宽，避免相邻块粘连；
3. 条目头信息（术语库名、条目 ID、只读标记）与正文之间留白，字号/颜色分级更清楚；
4. 用 `tests/render_main_ui.py` 之类的渲染截图做视觉回归（长定义、多语言、无定义三种样本）。

**风险 / 影响**

- 只改展示层 HTML/样式；若高度变化影响右栏滚动，需要同时调整 `res_panel` 的高度适配。

**验证方式**

- 视觉截图对照（长文本/多语言/空字段）；离线测试确认 `_tb_language_blocks` 输出结构不变。

## 5. 游戏语境栏拥挤

**状态**：待评估

**现状**

- `app/context_ui.py` 的 `ContextPanel`：前后各 2 段 + 角色既往译法；当前一行原文/一行译文、间距紧凑（`setMaximumHeight(225)`、间距 2–3px），长句显得挤。

**方案**

1. 保持“禁止横向滚动”的原则，但放宽纵向：每行允许最多 2–3 行自动换行，行高和行距调大，padding 增加；
2. 当前段高亮更明显；前后段用弱化色，层级更清楚；
3. 角色既往译法单独成块、可换行，不与上下文行粘连；
4. 高度上限适当提高（例如 260–300px），同时确认不挤压右栏其他面板。

**风险 / 影响**

- 语境栏变高会挤占右栏空间，需要和 TB 详情/QA 一起做高度分配测试；
- 内容仍只来自已缓存段，不改数据来源（见 `docs/LIMITATIONS.md` 游戏语境边界）。

**验证方式**

- 视觉截图：短句、长句、带 speaker、无 speaker 四种样本；
- 真机：`docs/SMOKE.md` N19 重跑。
